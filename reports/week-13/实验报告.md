## 四、Dependabot 配置（步骤 2）

### 4.1 配置文件

创建 `.github/dependabot.yml`：

```yaml
version: 2
updates:
  - package-ecosystem: "cargo"
    directory: "/"
    schedule:
      interval: "weekly"
      day: "monday"
      time: "09:00"
      timezone: "Asia/Shanghai"
    open-pull-requests-limit: 10
    labels: ["dependencies", "security"]
    groups:
      rust-deps:
        patterns: ["*"]
        update-types: ["minor", "patch"]

  - package-ecosystem: "github-actions"
    directory: "/"
    schedule:
      interval: "weekly"
    open-pull-requests-limit: 5
    labels: ["dependencies", "ci"]

  - package-ecosystem: "gitea-actions"
    directory: "/"
    schedule:
      interval: "weekly"
    open-pull-requests-limit: 5
```

### 4.2 配置要点

| 字段 | 值 | 作用 |
|------|-----|------|
| `package-ecosystem` | `cargo` / `github-actions` / `gitea-actions` | 监控 3 类依赖 |
| `schedule.interval` | `weekly` | 每周一检查更新，避免 PR 轰炸 |
| `open-pull-requests-limit` | 5-10 | 限流，避免 Dependabot spam |
| `groups` | `rust-deps` | 把 minor/patch 合并到一个 PR，减少 review 负担 |
| `labels` | `dependencies`, `security` | 便于筛选 |

### 5.3 SQL 注入风险

**本项目不存在 SQL 注入面**：
- 不接收用户输入的 SQL 字符串
- 所有数据操作通过程序化 API（`s.insert / s.delete / s.update`）
- 没有 SQL 解析器供外部使用

> 教学型项目刻意**不实现** SQL 字符串解析，因此从源头杜绝 SQL 注入。

## 七、思考与反思

### 7.1 安全边界定义

> "我是否开始学会定义'安全边界'？"

是。本项目的安全边界非常清晰：
- **入参边界**：只接受程序化 API 调用，不接受外部 SQL 字符串
- **内存边界**：Rust 类型系统 + 借用检查 + 0 unsafe
- **并发边界**：RwLock + HashMap 无 data race
- **依赖边界**：3 个直接依赖，0 漏洞

**这给 AI 的提示**："不要实现 SQL 解析器"——这本身就是一条安全护栏。

### 7.2 AI 能否理解"安全"概念？

> "AI 能理解'安全'这个概念吗？"

**有限地能**：
- AI 能识别 `unwrap()`、`unsafe`、`panic!` 这些"代码气味"
- AI 能对照 RustSec 数据库查依赖漏洞
- **但 AI 不能定义"什么算安全边界"**——这需要人来做架构决策

### 7.3 AI 不可替代的能力

> "AI 知道'这个功能在某些场景下可能有安全风险'吗？"

- AI 看到的是**当前代码** → 知道 `unwrap()` 在某种输入下会 panic
- AI 看不到**未来场景** → 不知道"3 个月后我会在网络服务里跑这个库"
- **人类负责"边界设计"，AI 负责"边界内的实现"**

### 7.4 自我提升

> "我是否开始学会从'安全'角度审查代码？"

通过本周练习，建立了 3 条审查习惯：
1. **入口检查**：所有 `pub fn` 都要么返回 `Result`，要么标 `unsafe`
2. **依赖面控制**：每加一个 crate 都要问"这个真的必要吗？"
3. **fail-safe 默认**：默认 deny（如 `cargo audit --deny warnings`），而非 allow
