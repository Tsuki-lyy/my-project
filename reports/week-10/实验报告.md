## 三、根因分析（步骤 2）

### 3.1 阅读基准测试代码

`qps_benchmark.rs` 中的 `qps_delete` 关键片段：

```rust
// 先批量插入 5000 行
for i in 0..BENCH_ITER {
    s.insert("users", vec![Value::Int(i as i64), ...]);
}
// 然后逐条 DELETE
for i in 0..BENCH_ITER {
    let filter = Expr::Binary { /* id = i */ };
    s.delete("users", Some(&filter));
}
```

DELETE 操作的关键路径：
1. **解析** WHERE 子句 → `id = i` 表达式树
2. **扫描** 全表行，逐行与过滤器比较（O(n) 比较）
3. **删除匹配行** → 触发行复制 / 向量收缩（`Vec::remove` 是 O(n)，5000 次删除的总成本是 O(n²)）
4. **更新索引**（虽然本项目无 B+Tree 索引，但维护了 `Row` 的版本标记）
5. **释放内存**（与 GC 类似，但 Rust 是 RAII 立即释放）

### 3.2 AI 辅助分析

向 Claude 提问：
> "SQLRustGo 的 DELETE 操作只有 ~3000 QPS，而 INSERT 有 ~80 万 QPS。为什么 DELETE 比 INSERT 慢 200 倍？可能的原因有哪些？"

| 可能原因 | 为什么影响 DELETE | 优化方向 |
|---------|------------------|---------|
| **1. `Vec::remove` O(n) 复杂度** | 每次 `delete` 内部用 `rows.remove(i)` 移动所有后续元素；5000 次删除 = 12.5M 元素移动 | 改用 swap-remove（O(1) 单次）+ 延迟压缩；或维护墓碑位图 |
| **2. 全表扫描过滤器** | 没有索引，每次都从 `rows[0]` 线性扫描到末尾 | 在主键上建 HashMap 索引，O(1) 定位 |
| **3. 行级锁/写时复制开销** | `RwLock::write` 在每次 delete 时锁整张表 | 改用行级 `Mutex<Row>` 或乐观锁 |
| **4. WHERE 表达式求值未优化** | 每行重新解析 `Expr::Binary` 并递归求值 | 预编译 filter 为闭包，缓存到 `Table` 上 |

### 3.3 我的判断

本项目作为教学原型，`MemoryStorage` 采用最简单的 `Vec<Row>` 存储是**有意为之**——为了让学生看到"裸实现"的全貌。但要满足 E-09 地板，必须在 Week 12 性能优化中至少落实两点：
- **swap-remove**（最小改动，5x 提速）
- **主键 HashMap 索引**（10-100x 提速）

两者叠加可以将 DELETE 从 ~3000 推到 ~50,000+ QPS，超过 E-09 地板。

### 4.5 "被 Gate 拦截"意味着什么

> 如果没有 Gate 系统：
> - 开发者可能直接合并一个"功能正确但性能不达标"的 PR
> - 上线后用户感受到响应迟缓，根因追溯到 DELETE/UPDATE 慢
> - 修复成本 = 重新发版 + 回滚 + 数据修复
>
> 有 Gate 系统：
> - 在合并前就发现 QPS 不到地板
> - 修复成本 = 改一个 PR + 重新跑 Gate
> - **没有生产事故**

这不是"代码好不好"的主观评判，而是"客观指标是否达标"的硬约束。

## 六、三层模型反思（步骤 5）

### 6.1 提示词层

| 观察 | 下次如何改进 |
|------|------------|
| 如果 PR 描述只写"实现 DELETE 操作"，AI/开发者会按"功能正确"实现 → QPS 200 | **PR 模板强制要求写量化目标**：例如 "DELETE QPS ≥ 10,000 on 5K-row table" |

### 6.2 上下文层

| 观察 | 下次如何改进 |
|------|------------|
| AI 看不到基准测试，不知道"2,977 QPS"是好还是坏；只看到代码，可能提"用 BTreeMap"反而更慢 | **向 AI 提供**：① 当前 QPS 数字 ② 期望地板 ③ 5K 行的数据规模 ④ 已有 benchmark 跑法 |

### 6.3 Harness 层

| 观察 | 下次如何改进 |
|------|------------|
| Gate 把"主观判断"变成"客观指标"：不论谁写代码、谁评审，DELETE < 10,000 就是不能合并 | **继续完善 Gate**：加 coverage 阈值（≥ 80%）、加 fuzz 时间（≥ 60s）、加 license check |

### 6.4 综合洞察

> **Harness 不是帮 AI 写代码，而是告诉 AI 哪里还不够好。**
>
> 本实验中：AI 已经写完了功能正确的 DELETE。**但 Gate 一跑，DELETE = 2,977 浮出水面**——AI 不知道这个数字不达标，开发者主观也容易"差不多就行"，只有 Gate 用绝对阈值把它揭示出来。这是 Harness 的核心价值：**把不可见的质量差距转成不可绕过的门禁**。

## 七、思考与反思

### 7.1 核心问题回答

**1. 如果没有 Gate 系统，DELETE 只有 ~3000 QPS 的版本会被发现吗？什么时候才会被发现？**
> 可能要到**生产环境**才会被发现：用户跑一个"清空 1 万行临时表"的操作，发现要等 3.4 秒，投诉给客服 → 客服反馈技术 → 技术复现 → 定位根因 → 紧急修 hotfix。**整个反馈链可能 1-2 周**，期间用户体验持续劣化。Gate 把这个发现时机从"生产事故后"提前到"合并前 5 分钟"。

**2. AI 在这个优化过程中能做什么、不能做什么？**
> AI 能：识别 `Vec::remove` 是 O(n)、建议 `swap_remove`、写出 HashMap 索引代码、生成 benchmark。
> AI 不能：**不知道 QPS 门槛是 10,000**——这是写在 E-09 ADR 里的业务约束，AI 没有上下文就只能猜。**没有 Harness 的 AI 写出的代码可能"功能正确但性能不达标"**。

**3. 为什么说 "Harness 不是帮 AI 写代码，而是告诉 AI 哪里还不够好"？**
> 本实验里：AI 写完了 v3.0.0 的 DELETE（功能正确），但 Gate BP2 报"DELETE = 2,977 < 10,000"。**AI 自己不可能知道"10,000"是底线**——它要么从 PR 模板里读到，要么从 Gate 输出里读到。Harness 提供的就是后者：一个外部的、客观的、不打折扣的"你还不够好"的反馈源。

### 7.2 局限与改进

- **本机 fmt 误报**：rustfmt 在 Windows GBK 控制台下 panic，是工具链问题而非代码问题。生产 CI 跑在 Linux 不会有此问题；后续可以把 fmt 检查改成调用 `rustfmt --check` 直接对单文件，避开 `cargo fmt` 的子进程派发。
- **样本量**：本机用 5,000 行压测是为了快速反馈。E-09 案例的 10,000 行压测是更稳的基线；下次可在 release profile（`--release`）下重跑，QPS 通常提升 5-10x。
- **Gate 自动化**：本实验 `gate_check.ps1` 是本地模拟；下一步（Week 11）会迁移到 GitHub Actions，配置 branch protection + required status checks。
