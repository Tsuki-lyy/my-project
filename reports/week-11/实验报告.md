## 二、CI 工作流配置（步骤 1）

### 2.1 BP1 / BP2 / BP3 / BP4 联动

`sqlrustgo/.gitea/workflows/ci.yml` 配置了 4 个并行/串行的 Job：

| Job | 名称 | 作用 | 触发条件 |
|-----|------|------|---------|
| `bp1-static` | BP1 静态 | build / fmt / clippy | 任何 push/PR |
| `bp2-behavior` | BP2 行为 | cargo test + QPS benchmark | bp1-static 通过后 |
| `bp3-risk` | BP3 风险 | oracle agent 检测 hot-path 文件改动 | 仅 PR，且需 bp1 通过 |
| `bp4-docs` | BP4 文档 | 检查 ADR/报告目录存在 | bp1 通过后 |

### 2.2 关键设计点

**Fan-out / fan-in 模式**：
```yaml
bp1-static ─┬─→ bp2-behavior
            ├─→ bp3-risk
            └─→ bp4-docs
```
- `bp1` 失败 → 全部下游 fail（快速失败 fast-fail）
- `bp1` 通过 → bp2/bp3/bp4 并行运行

**缓存加速**：
```yaml
- uses: Swatinem/rust-cache@v2
```
避免每次重编所有 crate，CI 时间从 8 min 降到 1-2 min。

**Branch protection 集成**（需在 GitHub/Gitea 后台配置）：
- `bp1-static` → required status check
- `bp2-behavior` → required status check
- 任一未通过 → 禁止 merge

### 2.3 与本地 `gate_check.ps1` 的关系

| 维度 | 本地 `gate_check.ps1` | CI `ci.yml` |
|------|----------------------|-------------|
| 触发 | 开发者本地手动 | 每次 push/PR |
| 环境 | Windows | ubuntu-latest |
| 编码 | 受 Windows codepage 影响 | 纯 UTF-8 |
| 作用 | 提前发现 + 教学演示 | 合并门禁 |

**二者并存**：本地 gate 是开发"红绿反馈"（秒级），CI gate 是合并"硬门禁"（分钟级）。

## 三、Agent 编排设计（步骤 2）

### 3.1 3-Agent 编排架构

`sqlrustgo/.gitea/workflows/agent-orchestration.yml` 实现 explore / librarian / oracle 三 Agent 并行：

```
                  ┌─────────────────┐
                  │  PR opened      │
                  └────────┬────────┘
                           │
                  ┌────────▼────────┐
                  │  agent-fanout   │  ← 抓 diff，打包成 artifact
                  └────────┬────────┘
                           │
        ┌──────────────────┼──────────────────┐
        │                  │                  │
   ┌────▼─────┐      ┌─────▼─────┐     ┌──────▼──────┐
   │ explore  │      │ librarian │     │   oracle    │
   │ (并发)   │      │  (并发)   │     │   (并发)    │
   └────┬─────┘      └─────┬─────┘     └──────┬──────┘
        │                  │                  │
        │ "找到 DELETE    │ "对照 Rust std  │ "预测性能回归"
        │  调用点"        │  API 文档"      │  风险等级"
        │                  │                  │
        └──────────────────┼──────────────────┘
                           │
                  ┌────────▼────────┐
                  │   synthesize    │  ← 汇总 3 份报告
                  └────────┬────────┘
                           │
                  ┌────────▼────────┐
                  │  PR comment     │  ← 报告贴回 PR
                  └─────────────────┘
```

### 3.2 三 Agent 详细分工（以 DELETE 优化 PR 为例）

| Agent | 分析任务 | 预期发现 | 实现位置 |
|-------|---------|---------|---------|
| **explore** | 静态扫描 PR diff，列出所有 `delete()` / `update()` / `insert()` 调用点；构建调用图 | "本 PR 修改了 `crates/storage/src/memory.rs:delete`，调用方为 executor.rs:95 和 integration test 1 处" | `explore-agent` job |
| **librarian** | 查外部资料库：Rust std doc、crates.io、本项目 ADR；验证 API 用法是否最佳实践 | "`Vec::remove` 是 O(n)，文档建议批量删除用 `retain`；`swap_remove` 更高效但破坏顺序" | `librarian-agent` job |
| **oracle** | 读取 diff + 历史 benchmark，预测性能回归风险；高风险则 fail CI | "diff 中出现 `rows.remove(idx)`，根据历史 PR #314，DELETE QPS 会掉到 ~3,000 → 高风险" | `oracle-agent` job |

### 3.3 为什么用 Agent 而非普通 CI 步骤？

| 维度 | 普通 CI 步骤 | Agent |
|------|-------------|-------|
| 输入 | 代码本身 | 代码 + 历史 + 外部文档 + 上下文 |
| 推理 | 模式匹配（如 grep） | 多步推理（"如果用 X 会有 Y 后果"） |
| 输出 | pass/fail | 结构化报告 + 解释 + 建议 |
| 失败处理 | 阻断 merge | 可配置（warn / block / 建议） |

**类比**：普通 CI 像自动售货机（固定按键 → 固定饮料）；Agent CI 像咖啡师（听你描述 → 推荐豆子 → 解释风味）。

### 3.4 本项目对 DELETE 优化 PR 的 3-Agent 设计

#### Agent 1：explore
- **任务**：
  1. grep `\.delete\(`、`\.update\(` 在 PR diff 中所有出现位置
  2. 反向追溯调用栈：`executor::execute → StorageEngine::delete → MemoryStorage::delete`
  3. 检查测试是否覆盖（grep `delete` 在 `tests/`）
- **预期发现**：
  - 修改文件：`crates/storage/src/memory.rs` 函数 `delete` 1 处
  - 调用方：1 处（`crates/executor/src/executor.rs`）
  - 测试覆盖：`crates/storage/tests/memory_extra.rs` 中已有 2 个 delete 测试

#### Agent 2：librarian
- **任务**：
  1. 对照 Rust 1.75+ std 文档，确认 `Vec::remove` / `swap_remove` / `retain` 复杂度
  2. 查阅本项目 `docs/adr/ADR-005-memory-storage.md` 是否已记录存储策略
  3. 交叉参考其他嵌入式 DB（sled、redb）的 DELETE 实现
- **预期发现**：
  - `Vec::remove(i)` 是 O(n-i)，批量 N 次调用 = O(n²)
  - 推荐方案：swap_remove + 主键 HashMap 索引
  - ADR-005 尚未记录 DELETE 性能问题，建议同步更新

#### Agent 3：oracle
- **任务**：
  1. 比对 PR 前后的 QPS benchmark 数据（来自 CI artifacts）
  2. 静态预测：如 diff 出现 `for i in 0..N { rows.remove(i) }`，DELETE 必然 < 5K
  3. 关联 Week 10 的 E-09 地板（10,000 QPS）
- **预期发现**：
  - 风险等级：**HIGH**（diff 中存在 `rows.remove` 模式）
  - 动作：在 PR 上贴警告，**要求开发者重跑 QPS benchmark 并贴结果**
  - 若 risk=high，CI 直接 fail，强制开发者重新提交

### 3.5 协调器（synthesize）的合并策略

```yaml
synthesize:
  needs: [explore-agent, librarian-agent, oracle-agent]
  steps:
    - 下载 3 份报告
    - 合成 Markdown 报告
    - 用 sticky-pull-request-comment 贴回 PR
```

**合并规则**：
- 3 个 Agent 都 OK → 报告状态 `READY TO MERGE`
- 任意 1 个 Agent 标 HIGH → 报告状态 `BLOCKED`，CI 退出码 1
- 仅 WARN → 报告状态 `REVIEW NEEDED`，CI 退出码 0

### 4.2 通知与升级路径

| 事件 | 通知方式 | 接收者 |
|------|---------|--------|
| BP1 FAIL | PR comment + email | 开发者 |
| Agent 报告就绪 | PR sticky comment | 评审者 |
| BP2 FAIL (QPS < 10K) | PR comment + Slack #dev | 开发者 + Tech Lead |
| 高风险 oracle 命中 | PR label `risk:high` + block merge | 开发者 + Maintainer |
| 全部 PASS | 自动 merge（如开启 auto-merge） | — |

### 4.3 关键设计：BP1 必须先过

无论 Agent 多智能、BP2 多严格，**BP1 静态检查是第一道闸**——它保证"代码起码能编译 + 起码符合规范"。如果编译都过不了，跑 Agent 是浪费算力，跑 QPS 是浪费时间。


## 五、反思与改进

### 5.1 与传统 CI 对比

| 维度 | 传统 CI | Agent-Augmented CI（本实验） |
|------|--------|----------------------------|
| 检查项 | 编译、测试、lint | 编译、测试、lint、调用图、API 文档对照、风险预测 |
| 反馈内容 | pass/fail 二元 | 结构化报告 + 建议 |
| 上下文 | 当前 commit | 当前 commit + 历史 PR + 外部 doc |
| 适用 | 中小型项目 | 大型项目 / 关键 hot path |

### 5.2 局限

- **CI 资源消耗**：3 Agent 并行会增加 3x 计算量。生产环境可错峰或采样
- **Agent 误报**：oracle 的 grep 模式可能误判（"看到 `rows.remove` 就高风险"过于粗暴）。需要不断调优正则
- **保密性**：Agent 可能需要访问私有 repo / 内部 wiki，需要 RBAC

### 5.3 下一步

- Week 12 性能优化后，把 `oracle-agent` 的 risk 阈值从"看到 remove 就高"改为"QPS 实际下降 > 10%"
- 接入真实的 LLM API（Claude / GPT）替代 grep，让 Agent 真正"理解"diff
- 写 ADR-008 记录 Agent 编排的引入动机与权衡
