## 三、性能分析（步骤 2）

### 3.1 火焰图替代：性能计数器分析

由于本机未安装 `cargo-flamegraph`（需要 Linux perf 工具），改用**性能计数器法**分析：

| 调用 | 单次耗时 (估) | 占比 | 备注 |
|------|-------------|------|------|
| `RwLock::write` 获取 | ~50ns | 30% | 每次 delete/update 都要抢写锁 |
| `Vec::remove` 内部 | ~100ns × n | 60% | **真正的热点**（v1） |
| `HashMap::get/insert` | ~50ns | 5% | v2 主要成本 |
| `eval_filter` | ~30ns | 5% | 表达式求值 |

### 3.2 性能瓶颈分析

**v1 三大瓶颈**：
1. **Vec::remove O(n)**：5000 次调用，每次移动平均 2500 行 → 总移动 12.5M 次
2. **全表扫描过滤**：每次都从 row[0] 扫到 row[n-1]
3. **RwLock 持锁时间长**：lock + scan + remove + unlock 一气呵成，并发退化

**v2 解决路径**：
- 引入 `pk_index: HashMap<i64, usize>` → DELETE 走 PK 时 O(1) 定位
- `swap_remove` 而非 `remove` → 单行删除 O(1)
- 维护索引一致性：swap 后修复被移动行的索引

## 五、重构实践（步骤 4）

### 5.1 重构目标：MemoryStorage → MemoryStorageV2

**重构原则遵守**：
- ✅ 小步重构：每改一个方法就跑一次 test
- ✅ 测试先行：先复制原 test 改名 `tests_v1`，加新 v2 test
- ✅ 频繁提交：每次优化单点 commit

### 5.2 重构前后对比（以 `delete` 为例）

#### Before（v1）

```rust
fn delete(&self, table: &str, filter: Option<&Expr>) -> Result<usize> {
    let mut t = self.tables.write().map_err(|e| Error::Storage(e.to_string()))?;
    let entry = t.get_mut(table).ok_or_else(|| table_not_found(table))?;
    let before = entry.rows.len();
    entry.rows.retain(|row| !eval_filter(filter, row)); // O(n) 扫描
    Ok(before - entry.rows.len())
}
```

**复杂度**：每次调用 O(n)；N 次单行删除 = **O(n²)**
**实测**：5,000 行 5,000 次删除 = 3,003 QPS

#### After（v2）

```rust
fn delete(&self, table: &str, filter: Option<&Expr>) -> Result<usize> {
    let mut t = self.tables.write().map_err(|e| Error::Storage(e.to_string()))?;
    let entry = t.get_mut(table).ok_or_else(|| table_not_found(table))?;

    // 快路径：filter 是 `id = N`，走 PK 索引
    if let Some(pk) = extract_pk_eq(filter) {
        if let Some(&idx) = entry.pk_index.get(&pk) {
            let last = entry.rows.len() - 1;
            let removed_pk = match entry.rows[idx].first() {
                Some(Value::Int(i)) => *i,
                _ => -1,
            };
            entry.rows.swap_remove(idx);     // O(1) 物理删除
            entry.pk_index.remove(&removed_pk);
            if idx != last {
                if let Some(Value::Int(swapped_pk)) = entry.rows[idx].first().cloned() {
                    entry.pk_index.insert(swapped_pk, idx);  // 修复被 swap 行的索引
                }
            }
            return Ok(1);
        }
        return Ok(0);
    }

    // 慢路径：retain + 重建 PK 索引
    let before = entry.rows.len();
    entry.rows.retain(|row| !eval_filter(filter, row));
    let removed = before - entry.rows.len();
    entry.pk_index.clear();
    for (i, row) in entry.rows.iter().enumerate() {
        if let Some(Value::Int(pk)) = row.first() {
            entry.pk_index.insert(*pk, i);
        }
    }
    Ok(removed)
}
```

**复杂度**：快路径 O(1)；慢路径 O(n) 扫描 + O(n) 重建索引
**实测**：5,000 行 5,000 次删除 = **801,706 QPS**（提升 267 倍）

## 六、ADR：记录性能优化决策

新建 `docs/adr/ADR-005-memory-storage-pk-index.md`：

```markdown
# ADR-005: MemoryStorage 主键索引选型

## 状态
已接受（2026-06-22）

## 背景
v1 的 DELETE 操作在 5K 行 5K 次单行删除场景下仅 3,003 QPS，
远低于 E-09 地板 10,000。根因：`Vec::remove` 是 O(n)，
N 次调用累计 O(n²)。

## 决策
引入 `HashMap<i64, usize>` 主键索引，快路径把 DELETE
从 O(n) 降到 O(1)。

## 权衡
- 内存：+8 bytes/行（PK + 索引值），5K 行约 40KB，可接受
- 复杂度：swap_remove 后必须修复被移动行的索引（一个 if）
- 兼容：原 `retain` 慢路径保留，行为不变

## 后果
- DELETE 提升 267x（3,003 → 801,706 QPS）
- UPDATE 无变化（仍全表扫描，留待 ADR-006）
- 新增测试 `pk_index_repaired_after_swap_remove`
```

> "AI 知道'这段代码在未来可能有问题'吗？"
>
> AI 看不到 6 个月后数据从 1K 涨到 1M 行时 `Vec::remove` 会变成灾难。
> **只有人类有"未来场景"的经验**。AI 能给的建议基于"现在的代码"，对"未来规模"无感。

### 7.3 自我提升

> "我是否能区分'AI 能帮我做的'和'必须我自己做的'？"
