### 步骤 8：多 AI 协同开发模式实践（15 分钟）

> 本周本地化体现："AI-1 做 LIMIT，AI-2 做 ORDER BY"，两人各自在 `feature/ai-parse-*` 分支开发。
> 当两人代码**都**修改了 `crates/parser/src/parser.rs` 时，因为改的是 `parse_select` 中**不同的位置**（LIMIT 在 WHERE 之后，ORDER BY 在 LIMIT 之后），git 自动合并成功，**未发生冲突**。
>
> 如果两人**同时**修改 `parse_select` 的同一行（例如都改 `Ok(Statement::Select { ... })` 的字段顺序），则会触发 7.3 演练的冲突。

**协作原则（已在工程中实施）**：
1. **分支隔离**：AI-1 / AI-2 各占一个 `feature/*` 分支 ✅
2. **PR 审查**：所有 feature 都经 PR 合并到 `experiment/week-09-*` ✅
3. **CI 检查**：`cargo test/clippy/fmt` 在合并前已通过 ✅
4. **冲突解决**：演练 7.1-7.3，方案记录在 §四-7 ✅

## 七、本周思考与反思

### 阶段：Context Engineering（上下文工程）

**重点**：学会提供足够的项目上下文，让 AI 理解代码结构。

| 自评问题 | 回答 |
|---------|------|
| 给 AI 描述时是否提供了足够的项目背景 | 是：每次都附带"修改哪个 crate、改动哪一层"的说明 |
| 哪些信息冗余 | AST 完整结构重复说明 |
| 哪些信息必要 | 文件路径 + 上下游 crate 依赖关系 + 已存在的相邻结构 |

### 遇到的问题与解决

| 问题 | 解决 |
|------|------|
| 改动 AST 字段后旧测试解构失败 | 同步更新 `parse_insert_and_select` 等解构点 |
| `columns: Vec<(...)>` 触发 dead_code | `#[allow(dead_code)]` 标注（暂时保留元信息） |
| 多 AI 同时改 `parser.rs` | 自动合并成功（因改的位置不同）；人为演练冲突解决流程 |
| Windows 终端长输出卡顿 | 用 `Select-String` 过滤关键行 + `Select-Object -First N` |
