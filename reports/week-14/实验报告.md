### 2.3 关键设计点

#### "必须 vs 最好"的区分

| 类别 | 门禁 | 必须 / 最好 | 触发 |
|------|------|------------|------|
| 代码 | build / test / clippy | **必须** | 任何失败 → BLOCK |
| 行为 | E-09 DELETE/UPDATE QPS ≥ 10K | **必须** | 任何失败 → BLOCK |
| 安全 | 0 RUSTSEC high / 0 unsafe | **必须** | 任何失败 → BLOCK |
| 质量 | 覆盖率 ≥ 70% | **最好** | < 70% → WARN，可放行 |
| 流程 | 分支策略 | **最好** | 缺失 → 人工 review |
| 文档 | 用户手册 | **最好** | 缺失 → 标注 N/A |

> 原则：**技术门禁硬，业务门禁软**——不要让 80% 覆盖率成为 release blocker，但要拒绝"0 unsafe"的红线。

## 三、门禁脚本编写（步骤 2）

### 3.1 脚本位置

`scripts/release_gates.ps1`

### 3.2 脚本结构

```powershell
# 7 大门禁统一执行
G01-build-debug          cargo build --all-features
G02-test-all             cargo test --all-features --locked
G03-clippy               cargo clippy --all-features --all-targets -- -D warnings
G04-fmt                  cargo fmt --all -- --check
G05-qps-{INSERT|SELECT|UPDATE|DELETE}
                         解析 QPS benchmark 输出
                         对照 E-09 地板 10,000
                         任何 DELETE/UPDATE < 10K → BLOCK
```

### 3.3 脚本亮点

- **自动定位项目根**：从 `PSScriptRoot` 推导出 project root
- **本地 target 目录**：`CARGO_TARGET_DIR=./.target`，避免污染
- **UTF-8 编码**：`[Console]::OutputEncoding = UTF-8` + `chcp 65001`，解决 Windows 乱码
- **结构化输出**：`$results` 数组汇总，最后 `Format-Table` 打印
- **退出码语义**：0 = 全部通过，1 = 至少一个门禁失败

## 六、思考与反思

### 6.1 "必须 vs 最好"的权衡

> "我设计的门禁规则，哪些是'必须'的？哪些是'最好'的？"

**必须**（hard gate，缺则不可发布）：
- 代码编译/测试/clippy
- 关键性能指标（E-09 地板）
- 安全底线（0 unsafe, 0 panic, 0 高危漏洞）
- 数据完整性（迁移、备份脚本可执行）

**最好**（soft gate，缺则警告）：
- 80% 覆盖率（教学项目可放宽到 60%）
- 完整用户手册（技术 README 即可）
- Branch protection（个人 repo 可豁免）

> **原则**：门禁太多 → 永远发不出；门禁太少 → 质量失控。

### 6.2 AI 能否判断"可发布"？

> "AI 能理解'这个功能虽然能 work，但还不够好发布'这个判断吗？"

**AI 能做**：
- 跑 cargo test / clippy / cargo audit → 客观 yes/no
- 解析 benchmark 输出 → 数字是否达标
- 检查 `unsafe` / `panic!` 数量

**AI 不能做**：
- "这个 PR 的设计哲学偏离了 ADR-005"
- "性能从 700K 涨到 800K 是有意义的，不是 noise"
- "这个 changelog 措辞会让用户困惑"

> **门禁是 AI 的舒适区，发布决策不是**。

### 6.3 自我提升

> "我是否开始学会设计'完整的规则体系'？"

是的。本实验让我建立了 3 层规则意识：
1. **代码层**：fmt/clippy/test 是最底层，不通过则无法 merge
2. **性能层**：E-09 地板是业务约束，把"主观性能争议"变成"客观数字对比"
3. **流程层**：branch protection + Dependabot + Agent 是治理工具

> "我是否能区分'技术问题'和'业务决策'？"
- UPDATE QPS = 2,956 **技术上是功能正确的**
- 但 **业务上未达 E-09 地板**
- 决策：推迟 v3.0.0 GA → v3.0.1，先做二级索引
