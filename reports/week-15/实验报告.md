## 三、版本标签（步骤 2）

### 3.1 标签创建流程

由于本机仓库未推送到 GitHub 远程，标签在本地创建并通过 PR 流程推上去。

```bash
# 在 develop/v0.3.0 分支上
git tag -a v0.3.0-alpha -m "Release v0.3.0-alpha - PK 索引 + CI/CD + Agent 编排"

# 推送标签
git push origin v0.3.0-alpha

# 验证
git tag -l
git show v0.3.0-alpha
```

### 3.2 SemVer 选型

本项目采用 [Semantic Versioning 2.0.0](https://semver.org/)：

| 阶段 | 标识 | 含义 |
|------|------|------|
| 0.x.y | 初始开发 | API 可能变 |
| x.0.0 | GA 首发 | 稳定 API |
| x.y.0 | 新功能 | 兼容 |
| x.y.z | 修复 | 兼容 |
| `-alpha` / `-beta` / `-rc.1` | 预发布 | 不稳定 |

> v0.3.0-alpha 是 0.x 阶段，**API 兼容性不保证**。v1.0.0 GA 时冻结 API。

## 七、思考与反思

### 7.1 独立设计发布流程

> "我是否能独立设计一个完整项目的发布流程？"

通过 6 周训练（Week 10-15），我建立了一条**7 步标准发布流程**：
1. 写 CHANGELOG
2. 跑 `release_gates.ps1`
3. 人工 review CHANGELOG
4. 创建 annotated tag
5. 推送 tag + 分支
6. 在 GitHub 创建 Release（粘 Release Notes）
7. 发邮件/Slack 通知

> **能独立完成**。关键是**写 ADR 记录决策**，下次复用时不用重新设计。

### 7.2 "规则"的价值和局限

> "我是否理解了'规则'的价值和局限性？"

- **价值**：门禁 = 把"质量争议"变成"客观检查"；规则 = 把"经验"沉淀为"流程"
- **局限**：规则无法捕捉"代码美学"、"未来兼容性"——这些需要人类判断

> **类比**：规则像交通灯（90% 场景够用），但赛车手需要看弯道（人类判断）

### 7.3 AI 能否理解"为什么要发布"？

> "AI 能理解'为什么要发布这个版本'这个商业决策吗？"

**不能**。原因：
- 商业决策 = 时机 + 资源 + 风险 + 战略
- AI 看到的是代码 / 性能数字，**看不到**：
  - "竞争对手 3 个月后会发类似产品" → 战略
  - "开发团队 6 月 1 日放假" → 时机
  - "客户 A 在等这个功能" → 资源

### 7.4 人类发布决策的非技术因素

| 维度 | 例子 | AI 能否理解 |
|------|------|------------|
| 战略 | "v1.0 必须赶在学术会议前发" | ❌ |
| 资源 | "团队只剩 2 人，下版本再修 bug" | ❌ |
| 风险 | "灰度 5% → 20% → 100%" | ⚠️ 部分 |
| 法务 | "欧盟 GDPR 合规问题" | ⚠️ 部分 |
| 品牌 | "这个功能会损害品牌一致性" | ❌ |
| 财务 | "每多 1 个 P0 bug 损失 $50K" | ⚠️ 部分 |

> **发布是 70% 技术 + 30% 商业**。AI 只能管 70% 的技术部分。

### 7.5 学期总结

> "我在这学期中学到的最重要的东西是什么？"

**最重要的认知**：**AI 越强，越需要 Harness**。

- AI 写代码快 → 但也会写错 → 需要 CI 拦截
- AI 找 bug 快 → 但也会找错 → 需要 ADR 定锚
- AI 优化性能快 → 但也会破坏 API → 需要 benchmark 量化

> **Harness = AI 时代的"项目管理"**。本学期的 16 个实验，本质是**学会给 AI 套上缰绳**。

### 7.6 如何向别人解释 AI 辅助开发？

> "我如何向别人解释'我是怎么使用 AI 辅助开发的'？"

我的 3 句话总结：
1. **AI 是结对编程伙伴，不是代写工具**：AI 出 5 个方案，我选 1 个；AI 写样板，我写设计
2. **规则让 AI 不跑偏**：门禁 + ADR + benchmark 三件套
3. **不可替代的是判断**：技术判断（选哪个方案）+ 业务判断（何时发布）+ 价值判断（这个功能该不该有）
